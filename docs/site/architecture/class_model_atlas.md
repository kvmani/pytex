# Class And Object Model Atlas

This page is the structural counterpart to {doc}`../concepts/library_structure`. That page explains
how PyTex is *organized*; this one shows what the code actually *is*: the classes, and the typed
relations between them.

Every diagram here is generated by importing PyTex and reading its declarations — base classes,
dataclass fields, resolved type annotations. Nothing is drawn by hand, so a renamed field or a new
composition appears the next time the figures are regenerated, and the test suite fails if the
committed figures no longer match the code.

:::{admonition} The one thing to know before reading
:class: important

**PyTex composes; it does not subclass.** Of 291 public classes, 274 are dataclasses and only 6
inheritance relations exist library-wide. A Doxygen-style hierarchy atlas would be nearly empty
here, and would describe a design PyTex does not have. The object-model diagrams — which show
composition and association — carry the real structure, and this page leads with them.
:::

## How To Read The Diagrams

| Notation | Meaning |
| --- | --- |
| Filled diamond at the upper end | **Composition** — a required field. The owner cannot be constructed without it. |
| Dashed line, plain arrowhead | **Association** — an optional or defaulted field. |
| Hollow triangle at the upper end | **Inheritance**, pointing at the base class in the usual UML direction. |
| `*` after a field name | The field holds a sequence of that type. |
| `name: Type` inside a card | A declared dataclass field, with its annotation shortened (`X?` is `X \| None`, `X[]` is a sequence of `X`). |
| Card tint | The subpackage the class belongs to. The module line under the class name says the same thing in text. |
| Faded edge | A relation spanning more than one layer, drawn lighter so local structure stays readable. |

A wide diagram keeps its drawn size and scrolls sideways inside its own frame rather than shrinking
to the text column, where its attribute lines would be too small to read. Open a figure in its own
tab to zoom.

Cards are placed so that **owners sit above the objects they own**. Reading a diagram downward
therefore follows construction dependency: nothing on a lower row needs anything above it.

Fields naming another card in the same diagram are listed first; the rest of a class's fields are
summarized as `+ n more`. `ProvenanceRecord` is deliberately absent from every object-model
diagram: nearly ninety classes carry it — each figure's legend states the current count — and
drawing those edges would say only that provenance is universal.
See {doc}`canonical_data_model` for what it holds.

## 1. Library Architecture

The core carries the canonical crystallographic model; texture, EBSD, diffraction and TEM build on
it; adapters sit at the external boundary; plotting presents. The numbers on the arrows are not an
intention — each one counts the typed field references that actually cross that boundary in the
source, so a layering violation would show up here as an arrow pointing the wrong way.

:::{figure} ../../figures/class_model_architecture.svg
:alt: Package-level architecture of PyTex, with the number of typed field references crossing each package boundary.
:figclass: class-atlas-figure
:class: class-atlas-image

Every arrow points toward the core. `pytex.core` holds no typed reference to any domain package —
a property {doc}`../concepts/how_pytex_differs` argues for and the test suite now checks.
:::

Two things this view makes concrete:

- **Diffraction is the heaviest core consumer** (52 crossing references), which is expected: its
  geometry, pattern and simulation objects all carry frames, phases and orientations.
- **Plotting and adapters barely appear as field references** (6 and 1). They take their inputs as
  call arguments rather than storing them, which is the boundary discipline
  {doc}`overview` describes — a presentation or translation layer must not accumulate state that
  belongs to the model.

## 2. Class Hierarchy

:::{figure} ../../figures/class_hierarchy.svg
:alt: Every inheritance relation in PyTex: the tilt-envelope family, the elastic tensor pair, the StrEnum vocabularies, and the structural protocols.
:figclass: class-atlas-figure
:class: class-atlas-image

The complete inheritance structure of the library.
:::

Subclassing is used in exactly one situation in PyTex: where several alternatives must be
interchangeable behind one interface.

- `TiltEnvelope` and its four subclasses are alternative *shapes* of the reachable tilt region of a
  TEM stage — rectangular, elliptical, polygonal, masked. A caller asks whether a tilt is reachable
  and does not care which shape answers. See {doc}`tem_tilt_navigation_foundation`.
- `ElasticTensor` gives `StiffnessTensor` and `ComplianceTensor` their shared tensor algebra; the
  pair differ in interpretation, not in mechanics.

Everything else is a frozen dataclass composed of other objects. That is a deliberate consequence
of the data-model doctrine in {doc}`canonical_data_model`: a scientific object should state what it
*contains* — which frame, which symmetry, which phase — rather than what it *is a kind of*.

## 3. Scientific Object Model

### Canonical Core

Frames, symmetry, lattice and phase, orientations, and the Miller objects. `Phase` is the join of
the model: one lattice, one symmetry specification, one crystal frame. A Miller index becomes a
`CrystalPlane` or `CrystalDirection` only once bound to a phase — which is what stops a bare index
triple from travelling through the library without its metric.

:::{figure} ../../figures/class_model_core.svg
:alt: UML object model of pytex.core: frames, transforms, symmetry, lattice, unit cell, phase, rotations, orientations, and Miller objects.
:figclass: class-atlas-figure
:class: class-atlas-image

Read downward: `ReferenceFrame` is at the bottom because nearly everything eventually rests on it.
:::

Concepts behind these objects: {doc}`../concepts/core_model`,
{doc}`../concepts/reference_frames_and_conventions`, {doc}`../concepts/miller_planes_directions`,
{doc}`../concepts/symmetry_and_fundamental_regions`. Constructors: {doc}`../api/index`.

### Orientation Relationships And Variants

The flagship transformation-crystallography model described in
{doc}`orientation_relationship_analysis_foundation`. An `OrientationRelationship` holds its
parallelism constraints as typed pairs of `CrystalPlane` and `CrystalDirection` objects, not as
index arrays — which is why a relationship can state its own conventions when asked to describe
itself.

:::{figure} ../../figures/class_model_transformation.svg
:alt: UML object model of the orientation-relationship and variant classes, and the report objects that carry characterization results.
:figclass: class-atlas-figure
:class: class-atlas-image

The report objects on the top row are the explainable-results surface: each carries the inputs and
provenance needed to reconstruct its own conclusion.
:::

### Texture

:::{figure} ../../figures/class_model_texture.svg
:alt: UML object model of pytex.texture: ODF, harmonic ODF, pole figures, kernels, and the inversion and reconstruction reports.
:figclass: class-atlas-figure
:class: class-atlas-image

Both ODF representations reach the same core symmetry and frame objects; the reports sit above the
products they describe.
:::

The discrete `ODF` and the band-limited `HarmonicODF` are separate objects rather than one class
with a mode flag, because their evaluation semantics differ. See
{doc}`../concepts/orientation_texture`, {doc}`../workflows/texture_odf_inversion`, and
{doc}`../workflows/harmonic_odf_reconstruction`.

### EBSD

:::{figure} ../../figures/class_model_ebsd.svg
:alt: UML object model of pytex.ebsd: crystal map, crystal map phases, grain segmentation, grain graph, boundary network, and the texture workflow.
:figclass: class-atlas-figure
:class: class-atlas-image

`CrystalMap` is the hub; grains, boundaries and texture outputs are all derived products that keep
a reference back to the map they came from.
:::

Note that `CrystalMapPhase` composes a core `Phase` rather than redefining one. This is the rule in
{doc}`../concepts/library_structure` that no subsystem may define its own private phase, symmetry
or frame model. Workflows: {doc}`../workflows/ebsd_grains`,
{doc}`../workflows/ebsd_to_texture_outputs`.

## How The Atlas Stays Current

```{list-table}
:header-rows: 1
:widths: 34 66

* - Component
  - Responsibility
* - `scripts/class_model.py`
  - Imports the public `pytex` modules and reads every class, field, annotation and base class into
    a model of nodes and typed relations.
* - `pytex.plotting.class_diagrams`
  - Lays the model out — layers by longest path, orders by barycentre sweeps, places by
    median-and-separate — and renders it in the canonical SVG style. Deterministic.
* - `scripts/generate_class_model_figures.py`
  - Chooses what each view looks at and writes the eight SVG assets in `docs/figures/`.
* - `tests/unit/test_class_model_atlas.py`
  - Fails if an annotation stops resolving, if the composition-first claim on this page stops being
    true, or if a committed figure differs from what the generator now produces.
```

Regenerate after changing the class model:

```bash
python scripts/generate_class_model_figures.py
```

A domain view names *modules*, not class names. Its roster is the most connected classes in those
modules plus a few pinned anchors and the core objects they reference, so a new class that becomes
central to a domain enters its diagram without anyone editing a list. Adding a whole new view means
adding one `ViewSpec` to the generator.

:::{note}
The atlas is rendered by PyTex's own SVG stack rather than by Graphviz. `pyreverse` and
`sphinx.ext.inheritance_diagram` both shell out to the `dot` binary, which the documentation build
does not otherwise require, and neither reads dataclass field types — the relation that carries
almost all of PyTex's structure. The typography used here is registered in
`docs/standards/visualization_style_guide.md` under the class-model diagram category.
:::
